# Donation images

The verified donation screen shows an initiative-specific image above **Share on X**, with a **Download PNG** link. Downloading saves a 1672 × 941 PNG; the donor can attach it to the X draft manually. The X intent link itself cannot upload the image.

The four active initiatives use owner-supplied artwork, converted to lossless WebP without changing the pixels. Only the selected template loads, after a receipt is eligible for sharing. Archived Burundi receipts use the original header, the Burundi photo and a correctly labelled replacement panel.

- CHOG cards and thank-you amounts use the donor's original selected `invoice.donationAmount`, falling back to the original amount for historical invoices. The NFT pool contribution is excluded. If the donor selected 300 CHOG and sent 333 instead of the requested 330, the card still says **300**. The full verified transfer is processed, and financial accounting retains the actual 302.727272727272727272 cause allocation. Exact received totals and allocations remain visible in receipt details; the original quote and QR never change.
- NFT cards show the invoice's actual `subsidyUsdc`, including historical 0.50 grants. They say **From the NFT pool** and **USDC**, distinct from the 1 MON verification payment.
- Public presentation uses at most two decimal places for CHOG and exactly two for NFT USDC. `formatDonationAmount` rounds half-up using BigInt and keeps the untouched selected amount separately. For example, a custom selected amount of 300.123456789012345678 CHOG displays as **300.12** on one clear line. The PNG adds a small **Approx. amount** caption when rounded; the X post says **approximately**. An original selection of 300 remains **300**, with no approximation label. Exact payment instructions, accounting and receipt details remain unchanged. Positive dust amounts below half a cent show **<0.01**, never zero.
- The renderer measures the static font's ink bounds, centres the readable amount within the inset window and reduces its size to fit a single line. There is no decimal continuation or large approximation symbol.
- A static Manrope ExtraBold Latin font ensures consistent weight in Safari and Chromium. Source: `@fontsource/manrope` 5.3.0; SIL Open Font License is included beside the asset.

Generation happens locally in the browser using fixed same-origin artwork. Images and filenames contain no invoice recovery ID, wallet address, nickname, NFT identifier or transaction hash. There is no upload endpoint or new server dependency. Blob download URLs are revoked on cleanup; loading failure leaves sharing available and offers a retry.

The card appears automatically inside the verified donation screen, immediately above **Share on X**. Its initiative and amount come from that receipt; there is no global gallery button or manual initiative selection. Publishing a leaderboard profile and receiving a delivered NFT grant keep the invoice active in this tab, so the receipt and image survive a page reload. **Donate again**, near the thank-you summary, returns to the form from a confirming or delivered receipt. It archives the invoice in private session history and clears the active checkout; independent finality checks continue and archived recovery data remains available in the recovery bundle.

## Validation

`test/donation-amount.test.mjs` covers exact BigInt rounding boundaries, carries, 18 decimal places, large values, integer/trailing-zero formatting, NFT fixed decimals, dust and malformed input. `test/donation-card.test.mjs` covers eligible receipt states, initiative/amount validation, separate exact and readable amounts, safe filenames, NFT attribution and single-line layout bounds. Existing sharing and invoice validation tests continue to cover the receipt boundary.

`test/payable-received-amount.test.mjs` checks that all three received-amount fields arrive together only after a verified deposit, remain within the original pilot limits, and exactly match the integer cause/pool split. Underpayment, malformed or partial metadata and changed quote fields are rejected. The 333 received versus 330 requested fixture keeps its exact 302.727272727272727272 CHOG cause allocation in accounting and details, while showing the original **300** selection on the card and preserving the original QR. Browser QA verifies the readable processing summary, original selected amount on thanks/downloaded card and exact receipt details in Chromium and WebKit.

Browser QA used synthetic, validated paid invoices with all non-GET API requests blocked: Chromium and WebKit; 1440, 390 and 320 pixel viewports; all four templates; a one-million CHOG donation; an 18-place decimal; current and historical NFT grants; archived Burundi; failed artwork loading and retry. Downloaded files decoded as full-size PNGs. For the four original CHOG templates, pixel comparisons confirmed that all changes stayed inside the amount inset and the rest of the artwork was preserved.

Receipt-lifecycle QA additionally restores a CHOG donation with an already published profile, reloads the page and verifies that the active invoice and inline image remain. NFT receipts receive the same check. Explicit **Donate again** actions return confirming and delivered receipts to the form, clear only the active invoice and preserve its archive. The global gallery control is absent. Tests make no real payments or profile publications.

## Care board totals

The public care board follows the same selected-donation rule. One wallet's earlier 1,500 CHOG plus an original 300 CHOG selection counts as 1,800, even when that invoice received 333 instead of 330. The overall completed-donation total includes anonymous gifts and adds the original 300 to 4,200 to show 4,500. Both projections still require the full verified actual source proof; stored nickname/profile amounts cannot override financial invoices. No invoices or settlement records are rewritten when the public projection changes.

Legitimately fractional selected amounts are summed exactly with BigInt before public formatting. The board displays at most two decimal places without an ellipsis, keeps the exact aggregate in its title, and marks rounded figures with a compact note. Large aggregate whole values remain exact. Reload the local payments worker to activate the public aggregation rule; deploying the frontend alone cannot refresh that process.
