### Проверки и активация

Финальный `npm run security:check`: **120/120 тестов**, сборка успешна, npm audit — **0 известных уязвимостей**. Включены version/integrity gate, корректное отображение неизвестной доступности и отдельные проверки блокировки до подписи/после persistence. Нулевой npm audit не доказывает отсутствие всех уязвимостей. Тесты используют только временные базы, новые тестовые ключи, RPC-моки и временные localhost-порты. Windows sandbox запрещал тестовый loopback и атомарный rename; полный прогон выполнен с разрешённым выходом из sandbox, без изменения защитных проверок приложения.

Дополнительно проверены crash/response loss/idempotency, сбой checkpoint после commit, same-hash NFT retry и restart, hard-invalid proof, очередь/бюджет, блокировка отправки при hold во время await, schema/DB/request-journal rollback, exact calldata и приватные веб-пути. Три исходных audit reproductions заменены regression assertions; H3 остаётся частичным смягчением.

В браузере проверены CHOG и NFT: старый API не выдаёт оплату через новый интерфейс; кнопки отключены, QR отсутствует, показано ожидание обновления. Ошибок консоли не найдено. Нажатий создания платежа не было.

Новый frontend требует `securityVersion: 2026-10-09-hardened-v1` и `integrityLocked: false`. **До owner-restart новые QR скрыты намеренно.** Старые IDs и отслеживание не удалены. Старый уже запущенный worker может продолжать свои операции; изменения исходников не меняют код в его памяти.

Активация для существующего локального пилота:

1. Сохранить открытые invoice IDs, дождаться безопасной точки и остановить платёжный терминал `Ctrl+C`. Не терять ссылку на платёж с уже отправленными средствами.
2. В папке `C:\Users\User\Documents\Codex\2026-10-07\ghb` выполнить **один раз при первой установке этой защиты** `npm run payments:integrity:enroll`. Команда создаёт согласованные бэкапы обеих БД и начальный checkpoint. Не читает vault и не отправляет средства. Начальная фиксация — не доказательство исторической полноты on-chain.
3. Выполнить `npm run payments:start`, пароль ввести **только локально**. Прежние адреса, пути derivation, получатель и лимит пула сохранены. Проверить version/integrity/readiness и существующий инвойс; не создавать новый для восстановления уже оплаченного.
4. При следующих проверках/backup остановить worker и использовать `npm run payments:integrity:check` / `npm run payments:backup`. Lease — loopback 4175; HTTP — 4174.

Если checkpoint уже существует или не совпадает, **не удалять, не перезаписывать и не обходить его через enrolment**. Нужна сверка БД, исходных signed hashes/nonces и истории цепочки. Существующий checkpoint находится в `work/payments/integrity/checkpoint.json`; базы — processor.sqlite и preview.sqlite. Нельзя восстанавливать старый checkpoint рядом со старой БД, чтобы «исправить» mismatch: это обходит replay-защиту.

Crash между commit и checkpoint может остановить последующий запуск до ручной сверки. Это сознательное fail-closed поведение. Кошельки/средства on-chain не удаляются; автоматического refund при блокировке нет. Локальный checkpoint не заменяет внешнюю неизменяемую или on-chain границу anti-replay.

## Модель угроз

| Кто атакует или где происходит сбой | Что защищаем | Ограничение модели |
| --- | --- | --- |
| Посетитель или бот | Очередь, бюджет, адрес/сумма, отсутствие чужих выплат | Локальный loopback сейчас ограничивает внешний доступ; после публикации риск возрастает |
| Посторонний сайт в браузере | Cross-site создание платежа, чтение закрытых файлов | Host/Origin помогают браузеру, но не являются паролем API |
| Компрометированный frontend/домен | Подмена QR, адреса и сети | Даже без wallet connection пользователь может отправить деньги на поддельный QR |
| Компрометированный API/пакет/процесс | Ключи, treasury, все депозитные адреса | Ключи находятся в том же процессе; программные лимиты обходятся при захвате процесса |
| Программа под User или администратор | Vault, пароль, RAM, исходники, база | ACL не создаёт защиты от этой категории |
| Ошибающийся или лживый RPC/Relay | Доказательства поступлений и доставки | HTTPS не доказывает правдивость chain data; нет независимого quorum |
| Сбой диска, питания или rollback backup | Replay, nonce, адреса, учёт денег | WAL/atomic помогают при штатном crash, но не решают восстановление из старого состояния |

## Высокие риски

### H1 Горячие ключи и API в одном процессе

**Статус: архитектурный риск, подтверждён кодом; компрометация не зафиксирована.**

[start-payments.mjs:27](C:/Users/User/Documents/Codex/2026-10-07/ghb/scripts/start-payments.mjs:27) разблокирует root, передаёт его обоим processors и поднимает HTTP API в том же процессе. Права User позволяют читать/менять проект. Установленный вредоносный пакет, RCE в Node, заражение ОС, кейлоггер или дамп памяти способны преодолеть защиту файла.

Последствия: потеря денег всех подконтрольных адресов. Лимит 10 USDC/day и allowlist получателей находятся в JS/SQLite, а не наchain EOA. Владелец украденного ключа может подписать обходную транзакцию на весь баланс. Шифрование vault и отсутствие wallet connection этого не предотвращают.

Приоритет исправления перед публичным запуском: отдельная минимальная служба подписи с другой учётной записью/хостом и независимой allowlist-политикой, web/API без доступа к keystore; HSM/KMS либо изолированный signer; маленький hot float и cold/multisig резерв. Просто другой Node-процесс под тем же User недостаточен. Для реального не обходимого украденным hot key лимита нужен подходящий on-chain policy contract или эквивалентная ограниченная схема полномочий.

### H2 Адреса разделены но секрет общий

**Статус: архитектурный риск при утечке ключевого материала.**

[custody-vault.mjs:4](C:/Users/User/Documents/Codex/2026-10-07/ghb/server/custody-vault.mjs:4), [nft-processor.mjs:30](C:/Users/User/Documents/Codex/2026-10-07/ghb/server/nft-processor.mjs:30): invoices и treasury производятся от одной HD-ветки. Путь `1000000/0` исключает совпадение адресов, но не ограничивает ущерб от компрометации root.

Non-hardened дочерний приватный ключ вместе с parent xpub позволяет восстановить parent private branch. Xpub лежит в незашифрованных метаданных vault; один xpub сам по себе не позволяет тратить средства. Это свойство BIP32, не ошибка ethers. [Первичная спецификация BIP32](https://github.com/bitcoin/bips/blob/master/bip-0032.mediawiki#security).

Нельзя экспортировать дочерний ключ «для удобного ручного возврата» в чат, frontend или менее защищённый инструмент, считая его независимым. Для production treasury и газового кошелька нужны независимые секреты либо тщательно спроектированные hardened границы с раздельным signer. Миграция должна сохранять возможность обслуживания уже выданных адресов; менять деривацию существующей базы на месте нельзя.

### H3 Публичные данные позволяют занять очередь NFT

**Статус: воспроизведено тестом AUDIT OPEN. Риск отказа в обслуживании, не доказанная кража пула.**

[nft-processor.mjs:168](C:/Users/User/Documents/Codex/2026-10-07/ghb/server/nft-processor.mjs:168) проверяет ownerOf, но не контроль заявителя над этим адресом до `reserve`. После трёх заявок четвёртая отклоняется по capacity. Заявитель знает только публичные holder/token IDs и не оплачивает MON.

В тесте три инвойса без proof заняли все места, бюджет показывал ещё 17 доступных claims, а `nftPaymentsEnabled` оставался true. Неоплаченные слоты позже истекают, но их можно занимать повторно. У CHOG тоже три публично создаваемых неоплаченных инвойса могут занять очередь, там окно до 20 минут. Лимит IP не является достаточной защитой после публикации.

Нужно изменить порядок резервирования: challenge/session и антибот до выдачи, лимиты на holder/NFT/IP, глобальные ограничения и понятный статус capacity. Без wallet connection можно принимать proof через перевод, но резерв до proof должен быть коротким и устойчивым к злоупотреблению; нельзя просто попросить пользователя платить, когда субсидия ещё не гарантирована. Политика конкурентных заявок требует отдельного решения и тестов.

### H4 Восстановление старой базы может разрушить anti replay

**Статус: архитектурный сценарий восстановления, не воспроизведение на пользовательских данных.**

Адресный индекс, использованные NFT/day, funding event IDs и signed outbox находятся в SQLite. Уникальные индексы защищают актуальную базу, но не историю, которую оператор откатил старым backup. Vault без базы не знает, какие grants уже были отправлены. При rollback worker может выдать прежний адрес или заново зарезервировать использованный NFT/day, а отправку выполнить с актуальным on-chain nonce.

Нужны согласованные backup и проверенный disaster recovery: запрет выдачи после восстановления, восстановление истории цепочки и подписанных журналов, внешняя фиксация checkpoint/расходов, затем явный unlock. Рекомендуется отдельная on-chain replay/budget граница для NFT-пула. Не тестировать rollback на реальных деньгах и не удалять ledger для «починки».

## Средние риски

### M1 Временный RPC сбой навсегда отправляет NFT платёж на ручной разбор

**Статус: воспроизведено.**

[nft-processor.mjs:99](C:/Users/User/Documents/Codex/2026-10-07/ghb/server/nft-processor.mjs:99) переводит в `manual-review` любой exception проверки, включая transient RPC timeout. Следующие `tick` этот статус не выбирают. Резерв сохраняется и занимает одно из трёх мест. Это безопаснее второй выплаты, но donor уже мог оплатить 1 MON, а продолжения нет.

Тест зафиксировал candidate MON-transfer, сымитировал краткий RPC outage и показал отсутствие повторного proof чтения в следующем tick. Нужны отдельные состояния retryable/network-failure и hard-invalid, bounded backoff и ручное возобновление **того же** hash после строгой повторной проверки. Нельзя выпускать новую выплату или просить платить заново.

### M2 Rate limit общий для пользователей за прокси

**Статус: воспроизведено.**

[payment-service.mjs:31](C:/Users/User/Documents/Codex/2026-10-07/ghb/server/payment-service.mjs:31) использует socket.remoteAddress и один лимит 60/min для чтения и создания. Vite proxy даёт общий loopback peer. Несколько вкладок/посетителей делят bucket. После 60 GET от разных условных клиентов третий получил 429; это не нагрузочный тест живого сервера.

Последствия: пропажа polling/QR и ложное впечатление остановки платежа, блокировка новых заявок одним клиентом. Нужны отдельные лимиты create/status, per-session плюс общий бюджет и корректный trusted-proxy механизм. Просто доверять любому `X-Forwarded-For` нельзя: текущие тесты правильно запрещают такой обход.

### M3 Отнесение CHOG доставки к заказу зависит от Relay API

**Статус: подтверждено статическим разбором, компрометированный Relay не моделировался в mainnet.**

[chog-processor.mjs:148](C:/Users/User/Documents/Codex/2026-10-07/ghb/server/chog-processor.mjs:148) принимает кандидаты txHashes из Relay status после проверки origin/destination и source hash. Затем проверяет canonical finalized USDC Transfer получателю с достаточной суммой. Но не проверяет on-chain settlement event с конкретным подписанным orderId; sender USDC-события также не связывается с исполнителем заказа.

Ошибающийся/скомпрометированный status API, знающий публичный source hash, может указать другой ещё не учтённый перевод подходящей суммы тому же получателю. Это риск ложного `delivered` и неправильного attribution, не автоматический произвольный перевод средств пользователем. `delivered_events` препятствует повторному использованию уже учтённого события, но не доказывает принадлежность первого события.

Нужно проверять протокольную связь orderId с settlement и конкретным transfer либо явно считать Relay доверенной стороной и не называть результат независимым доказательством исполнения заказа. Одного равенства суммы или sender недостаточно для пакетных платежей.

### M4 Доверие единственному RPC и внешним протоколам

Canonical hash, chain ID и finalized tag проверяются через тот же RPC. Лживый RPC может дать внутренне согласованный вымышленный ответ. Нет quorum независимых операторов или собственного узла. Для денег нужен сверочный второй источник и fail-closed при расхождении; это снижает риск, но не заменяет cryptographic light-client verification.

Nad.fun/Uniswap/Relay закреплены адресами, но код не контролирует изменения реализации upgradeable протоколов или прав управления ими. Валидация signed Relay order не аудирует безопасность depository, solver и bridge. Реальный mainnet fork с этими контрактами и анализ их upgrades в эту проверку не входили.

### M5 Ручное восстановление и поздние оплаты не завершены

Ошибочная сумма, несколько депозитов, expired quote, reverted swap/bridge, неоднозначный broadcast или изменение владения NFT требуют разбора. Для произвольного безопасного refund/recovery нет законченного локального инструмента. 1 MON остаётся на отдельных адресах; остатки 5 MON газа также автоматически не возвращаются.

Просроченные NFT-инвойсы после освобождения больше не сканируются в `tick`. Поздние средства не исчезают on-chain, но автоматической реакции нет. Дополнительные депозиты после перехода инвойса в обработку/завершение не охвачены полноценной системой учёта всех входящих средств.

Нужен отдельный reconciliation registry всех поступлений, просмотр активов по каждому адресу, recovery с сохранением старых hashes/nonces, политика возврата и журнал действий. Возвращать автоматически на `tx.from` небезопасно для бирж и контрактов. Команду recovery необходимо отдельно тестировать до её использования.

### M6 Нет полноценной production границы веб приложения

`webBoundary` задаёт nosniff, X-Frame-Options, Referrer-Policy и Permissions-Policy. HTML frontend не получает Content-Security-Policy из этого middleware. CSP на API JSON не защищает HTML. Скриптовый injection в просмотренном интерфейсе не найден; отсутствие CSP само по себе не доказывает XSS.

Vite работает как локальный dev-server, не утверждённая production-публикация. Секретный vault остаётся внутри дерева проекта и защищается deny list/ACL: ошибка web-конфига повышает риск раскрытия зашифрованного файла. HTTPS, reverse proxy, cookie/session политика, CSP с разрешёнными источниками и раздача только `dist` должны быть спроектированы отдельно. Сам keystore и база должны находиться вне public/build root и быть недоступными web-пользователю.

## Дополнительные функциональные и операционные ограничения

- **NFT restore UI:** [App.tsx:142](C:/Users/User/Documents/Codex/2026-10-07/ghb/src/App.tsx:142) и `chooseCause` учитывают active CHOG ID, но не NFT ID. После reload интерфейс может не открыть нужный NFT checkout и при выборе другой инициативы показать существующий Burundi-инвойс рядом с чужой карточкой. Backend recipient остаётся закреплённым; риск путаницы и доверия. Нужны общий active-invoice state, привязка инициативы/режима и тест reload/navigation.
- **Хранение только в sessionStorage:** потеря вкладки/сессии может потерять доступ к invoice ID, хотя деньги/состояние остаются на сервере. Нужна безопасная recovery-ссылка или история без раскрытия чужих данных.
- **Нет POST idempotency key:** ответ создания может потеряться после успешной записи. Повтор создаёт новый CHOG invoice либо NFT duplicate reservation отказ. Это не двойная выплата, но orphan slot и неудобное восстановление.
- **Общее время обработки не ограничено обещанием UI:** 0.001 ETH threshold может остановить новые подписи, если остаток станет ниже порога; nonce, market movement, finality и provider outage тоже вызывают паузы. Нужны метрики и alerts, не обещание 25 секунд.
- **Source quote persistence:** сохранённые sale/swap параметры могут устареть во время паузы. Slippage защищает от слишком плохого исполнения, но возможен revert или длительная остановка. Рекотировка допускается только до подписи соответствующей фазы; unknown signed transaction нельзя заменять вслепую.
- **Условия возврата Relay:** адреса refund проверяются, но отдельная пользовательская политика для refund deadlines/minimumAmount/extraData не сформулирована. Signature solver не заменяет одобрение этих условий. Нужны документированные допустимые значения и негативные тесты.
- **Source journal не изолированный policy signer:** он проверяет chain/sender/nonce/gas/phase, но не полностью проверяет calldata каждой фазы независимо от builder. Это защита от повторной отправки, не граница против захваченного процесса.
- **Статические данные:** суммы Giveth и статус verified в карточках зафиксированы в `App.tsx`, могут устареть. Broadcast не подключён. Прямая доставка USDC не гарантирует учёт доната/вознаграждений на Giveth.
- **Документация:** старые файлы содержат исторические preview/Ethereum-only утверждения. Текущий источник архитектуры — новый документ; старый ARCHITECTURE.md получил явную ссылку. Старые аудиты сохраняются как история, не как актуальное разрешение на запуск.

## Работающие защитные меры

1. Нет wallet approval или подписи через текущий frontend. Ни пароль, ни приватный ключ не требуются от донора.
2. Секрет хранится в зашифрованном keystore, создание использует exclusive write и проверку восстановления; ACL ограничен. Это at-rest защита, не защита от malware.
3. Уникальные адреса и случайные invoice IDs. Branch binding и SQLite transaction предотвращают обычное повторное выделение индекса.
4. Нет произвольного получателя от браузера. Выплаты закрыты на Burundi; другие карточки не означают разрешённый маршрут.
5. Подтверждение по canonical finalized receipt, точному токену, chain, event provenance и сумме; symbol `USDC` не считается доказательством.
6. NFT proof проверяет direct 1 MON от holder и ownerOf, а replay блокируется по транзакции и NFT/day.
7. Ledger резервирует доступные деньги атомарно и применяет дневные лимиты. Funding dedup включает chain/hash/logIndex, сохранены оба согласованных источника.
8. NFT outbox проверяет точный `transfer(beneficiary,500000)`, отсутствие ETH value/лишних данных, сеть и газ. Подпись и бюджет фиксируются до broadcast.
9. Повтор после timeout сохраняет исходные bytes/hash/nonce. Неизвестный результат не приводит к автоматической новой выплате.
10. CHOG approvals точные; роутеры и Relay depository закреплены, Relay order hash/signature проверяются, calldata собирается локально.
11. Закрыты служебные веб-пути, включая raw imports и варианты Windows-путей. API ограничивает Host, Origin, размер/формат, число запросов и соединений.
12. UI разделяет receipt и finality, проверяет неизменность инвойса, скрывает QR при остановке и предупреждает не платить повторно.

## Что означает хранение ключей для владельца

| Сценарий | Что реально защищает | Что остаётся под риском |
| --- | --- | --- |
| Кто-то узнал публичный treasury address | Приватный ключ не вычисляется из адреса практическим способом | Видны публичные балансы и переводы |
| Скопировали только зашифрованный vault | Сильный уникальный пароль и KDF замедляют offline подбор | Слабый/повторный пароль, будущая утечка пароля; xpub не зашифрован |
| Украли пароль вместе с vault | Существенной защиты средств этой ветки уже нет | Все связанные адреса |
| Вирус работает под User при запуске | ACL и hidden prompt не спасают | Файл, ввод, память, изменение кода перед unlock |
| Украден ключ разблокированного treasury | Программный лимит не ограничивает злоумышленника | Весь баланс treasury; общий HD риск зависит от доступного xpub/ключей |
| Подменили сайт/QR без доступа к серверу | Не получают автоматически весь внешний кошелёк донора | Могут украсть сумму, которую донор вручную отправит на поддельный адрес |

Ни пароля, ни vault, ни seed нельзя передавать в чат. Проверка сложности фактического пароля, шифрования диска, антивируса, дампов процесса, облачной синхронизации Documents и всех внешних backup в этот аудит не входила. Нельзя утверждать, что на компьютере нет вредоносного ПО.

## План исправлений до публичного запуска

**Первая очередь — безопасность хранения и денег.** Отделить signer от web/API, вынести секреты из проекта, разделить treasury и invoice keys, оставить небольшой hot float, определить on-chain либо независимую signing policy. Подготовить согласованный backup/recovery и запрет запуска после rollback без сверки. Не менять ключи/адреса существующих инвойсов без миграционного плана.

**Вторая очередь — доступность и восстановление.** Исправить H3, M1 и M2; добавить explicit capacity, idempotent invoice creation, безопасное продолжение того же proof/hash, recovery интерфейс и сверку поздних/лишних депозитов. Исправить восстановление NFT-инвойса и выбранной инициативы.

**Третья очередь — доказательства и внешние зависимости.** Проверить on-chain Relay order settlement attribution, refund terms, протокольные deployments и upgrades, добавить независимый RPC и alerts на расхождения, подписи и balances.

**Четвёртая очередь — deployment и испытания.** Production build за HTTPS, web-сервис без доступа к signer/storage, CSP и доверенная proxy-конфигурация, structured secret-free errors, мониторинг и план остановки. Контролируемая владельцем NFT-выплата end-to-end; mainnet-fork и fault injection на каждом переходе; отдельный внешний аудит перед ростом бюджета.

Действующие кошельки, лимиты, процесс и финансовые записи в ходе аудита не изменялись. Добавлены документация и три воспроизводящих теста. Открытые риски не считаются устранёнными.
